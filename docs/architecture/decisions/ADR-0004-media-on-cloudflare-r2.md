# ADR-0004: Media on Cloudflare R2

- Status: Accepted
- Date: 2026-10-10

## Context

The proposal asks for S3-compatible object storage with signed uploads and downloads for avatars, ride and post photos, and GPX files. The API runs on Cloudflare Workers.

## Decision

- Store media in **Cloudflare R2**, one bucket per environment, no public access.
- Uploads go directly from the client to R2 with a short-lived presigned PUT URL. The Worker never proxies file bodies.
- Presigning uses R2's S3-compatible API with a Workers-compatible signer such as `aws4fetch`. Server-side reads, validation and deletes use the R2 bucket binding.
- Object keys are generated by the server. Client filenames are stored as metadata at most and never used in a key.
- After upload the API verifies real size and content signature before marking the asset usable.
- Downloads use short-lived presigned GET URLs issued after a visibility check.

## Consequences

- Same platform as the API, an S3-compatible interface, and a binding for server-side access.
- Presigned URLs cannot enforce everything at upload time, so post-upload verification and a cleanup job for unconfirmed uploads are required parts of the design, not extras.
- Image resizing is not solved here. Start with on-device resize before upload; decide on a server-side transformation service when it is actually needed.
- Because the interface is S3-compatible, moving to another provider is a configuration and data-copy exercise.

## Alternatives considered

- **AWS S3 or another S3 host.** Works, but adds a second cloud account for no MVP benefit.
- **Uploading through the Worker.** Simpler validation, but runs into request size and memory limits and wastes CPU time.
